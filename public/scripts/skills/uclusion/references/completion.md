# Prepare and publish a completion package

The implementation or standalone owner prepares the concrete package for its reviewed finished scope. Use the reviewed repository changes and exact notification scope from current evidence.

List the actual available actions in this order:

1. Commit only the identified reviewed changes, naming repositories/files or a compact unambiguous scope.
2. Push only those commits.
3. Clear the exact finished whole job, otherwise its review and identified resolved tasks; for a standalone bug, the exact bug/replies scope supplied by its owner.

Omit commit/push when no repository work applies. Explain what `all` selects. Other actions retain their independent permissions, and an actual notification clear additionally needs explicit chat permission for that exact scope.

For a job, pass the narrative to `ask_for_review` as `report` and this package as `completion_package`, which the tool appends last. A newly created review can be named as “this review”; its saved receipt supplies the canonical thread identity. For a bug fixed in this session, publish with `add_info` on its resolved bug thread when the standalone owner confirms the resolution trigger.

End with a short invitation on the package thread: “Reply `all`, or tell me in your own words what you want.” If a non-AI, non-advisory human response to the applicable package has already arrived, forward its exact identity/message to operation instead of repeating the invitation. Operation owns selection interpretation, authorization and execution.

Return the canonical saved thread and exact confirmed package text immediately for coordinator presentation, before follow-on work. Later waits return the exact package/reply identity and pending action/terminal state; present the full package once. Return a bounded request to the caller for reply handling or unfinished selected actions. Carry your substantive completion confirmation for that scope, its target/applicable-contract identities and known receipts with that request.
