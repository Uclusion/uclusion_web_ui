# Discovery requests and results

Dispatch work discovery only at startup with no assigned work, when confirmed assignment endings leave no other assigned work, or on an explicit human request for other work. While any work remains assigned, request a list for information only; do not let that request select or claim work. A later explicit human choice may assign additional work to another helper or switch the work it identifies. Preserve existing assignments unless that choice changes them. Listener restarts, turn endings, package waits, manual stage requests and intermediate handoffs do not start discovery. A pending completion offer or notification cleanup does not prevent discovery once the finished assignments have ended and no other assigned work remains.

Retain one `operation` helper for work discovery within the same coordinator session, workspace and package. Start it fresh, preserve its identity through compaction, and request one new `find_work` result for each authorized discovery request; present only that result, without prefetching or polling. Replace it with a fresh helper when unavailable, its context cannot be recovered, or the session, workspace or package changes. Use separate fresh `operation` helpers for bounded creation, reopen, inbox or workspace-history requests. Tell the discovery helper whether selection and claiming are permitted for this request; it interprets the returned selection and claim directions.

Present the complete current numbered list and its directions for selection, onboarding and automatic work selection immediately on receipt, including while the helper is still running, unless presentation in the chosen conversation is already confirmed. Say that the human can choose an item by replying with its number. Preserve the returned order, exact codes, names and stored bug severity, and do not present the choices again as a separate question or in another order. Allow selection under those directions without waiting for maintenance or repeating the list when later receipts arrive. Carry any confirmed selected or claimed work identity to its responsible role; a list requested only for information assigns no work.

For a native Codex bounded claim request, read [claims.md](claims.md) completely.

For an empty work-selection result, follow any returned directions explicitly marked for one-time first-session onboarding before other empty-list handling. An ordinary empty list does not establish that status. Follow returned directions for automatic work selection only within the current request's authorized scope. For other empty lists when a human is active in chat, ask exactly: "Your find work list is empty. Would you like instructions for adding and working on a job?" On yes, explain the returned directions for creating jobs, selecting work or using `find_work`, job stages, assistance on Debatable jobs and Poke AI.

After an empty or fully deferred current list, authorize one bounded `request_work` call for that result only when no work is assigned, no human is active in chat, and no request is pending, confirmed or uncertain for the current period without available work. Retain the authorization and confirmed, failed or uncertain outcome across work-list helper replacement and compaction. Reconcile an uncertain attempt before authorizing another; pass any prior receipt or unfinished outcome with the action. Cancel an unperformed authorization if chat or assignment changes make it ineligible.

Start a returned maintenance request separately in a fresh `backlog-maintenance` helper with its exact window, batch and receipts. Preserve completion, failure and unfinished outcomes through compaction. Maintenance does not delay selection or cause another discovery call.
